# 第三方库适配层规范

## 1. 总体原则

适配层是项目内部 API 与第三方库之间的边界。适配层应小而稳定，只暴露项目真正需要的能力。

必须做到：
- 第三方库只在对应适配层中直接导入。
- 对外 API 使用项目自己的类型，尽可能避免把底层库类型泄漏到业务层。
- 每个适配层有统一 `index.ts`。
- 适配层内部实现可替换，对外 API 尽量兼容。
- 适配层必须有测试，尤其是错误处理、状态转换和边界行为。

不要求：
- 不要把第三方库所有 API 都复制一遍。
- 不要为每个简单函数再增加一层没有价值的包装。
- 不要为了“彻底隔离”而损失第三方组件必要的扩展能力。

## 2. Ant Design：`src/adapters/ui/`

### 责任
- 统一主题、尺寸、默认属性和项目视觉规范。
- 对高频组件进行封装，例如 Button、Input、Select、Table、Modal、Drawer、Form。
- 统一 message、notification 等全局反馈入口。
- 对 Table 等复杂组件统一项目级分页、空状态、加载状态和数据协议（确有需要时）。

### 规则
- 业务代码不得 `import { Button } from 'antd'`。
- 简单组件可薄封装；复杂组件应提供项目级 Props 和行为。
- 不要把 Ant Design 的全部 Props 无条件暴露到业务层。确需扩展时，通过明确的 `nativeProps` 或受控扩展策略提供。
- Ant Design 主题配置集中管理。
- CSS 覆盖集中管理，不在业务页面依赖 Ant Design 内部 DOM 结构。

## 3. Axios：`src/adapters/http/`

### 责任
- 维护统一 Axios 实例。
- 统一 Base URL、超时、公共请求头。
- 统一 Token 注入和响应处理。
- 统一网络错误、HTTP 错误和业务错误的转换。
- 支持请求取消、上传下载等项目确实需要的能力。

### 规则
- 业务 API 放在 `services/`，页面不得直接请求。
- 业务代码不得导入 Axios。
- 不要假设所有后端响应都只有一种格式；根据真实接口协议定义 `ApiResponse<T>` 和解包规则。
- Token 的读取应依赖项目定义的认证接口或注入函数，不要让 HTTP 适配层直接依赖某个页面或业务 Store。
- 拦截器只处理通用协议，不处理某个页面的业务跳转。
- 不要把所有错误都转换成空数组或 `null`，避免吞掉错误。

## 4. Zustand：`src/adapters/store/`

### 责任
- 统一 Store 创建入口。
- 统一项目使用的中间件策略（如 persist、devtools，按需启用）。
- 统一 Store 相关公共类型和工具。

### 规则
- 每个业务域独立 Store。
- Store 暴露状态和 Action，不允许组件直接修改内部对象。
- 组件使用 selector 订阅所需状态，避免无意义的全量订阅。
- 只有确实需要跨刷新保留的状态才持久化。
- 不要在适配层写入具体业务状态。
- 不要为每个 Store 重复创建包装器。

## 5. React Router v6：`src/adapters/router/`

### 责任
- 统一路由创建方式、导航封装、权限边界和错误页面约定。
- 统一路由懒加载和路由元数据（按项目需要）。
- 业务路由表放在 `src/router/`。

### 规则
- 业务组件使用项目封装的导航、参数读取 API。
- 路由配置层允许按需使用 React Router 类型，但业务页面不直接导入底层 Hook。
- 不要把路由权限判断散落在页面组件中。
- 示例采用 React Router v6.4+ Data Router API。若项目版本较早，必须使用该版本支持的 API。

## 6. Tailwind CSS

Tailwind 是构建期样式工具，不需要人为创建运行时 Adapter。

项目应统一：
- 主题颜色、字号、间距、圆角、阴影和断点；
- 全局 CSS 入口；
- 常用布局组件和复用样式；
- Ant Design 与 Tailwind 的样式边界。

Tailwind 版本不同，配置方式可能不同（例如 v3 与 v4 的主题配置方式不同），应以项目安装版本为准。

## 7. Vite、React、TypeScript

它们属于项目基础设施，不需要无意义地包装成运行时 Adapter。

- Vite：集中管理构建、别名、代理和环境变量。
- React：遵循 React 官方组件与 Hooks 模型。
- TypeScript：统一严格类型配置和公共类型约定。

## 8. 升级流程

1. 查看第三方库升级说明和 Breaking Changes。
2. 明确项目实际使用的 API 范围。
3. 只在对应适配层修改实现。
4. 保持项目内部 API 不变；无法保持时提供迁移方案。
5. 运行适配层测试、类型检查、业务测试和生产构建。
6. 更新适配层文档和依赖版本记录。
